| `places_backup_20260810.csv` | `places` 전체 883행(활성 844 + 비활성 39), 39개 컬럼. 재조회 직전 스냅샷이다. |

같은 날 TourAPI 목록 스냅샷과 대조 결과는 `supabase/data/places_api_snapshot_20260810.csv`,
`places_reconciliation_20260810.csv`에 있다. 목록은 `20260808` 기준 대비 **신규 0 /
삭제 0 / 수정 0**이었다 — 이번 실행의 목적은 목록 갱신이 아니라 새 컬럼 적재였다.

## 이 시점에 무엇이 바뀌었나

목록은 그대로고 상세 컬럼만 바뀐다. `update_operating_details`가 쓰는 값이다.

- `info_center_raw` — 안내처(전화번호). 0건 → 632건
- `baby_carriage_raw` / `pet_raw` / `credit_card_raw` / `restroom_raw` — 0건 → 97 / 2 / 181 / 112건

## 미완결 — 142건이 남았다

**활성 844건 중 702건만 채웠다.** 나머지 142건은 `detail_fetch_status='failed'`
상태이며 값이 비어 있다. TourAPI `detailIntro2`의 **일일 요청 한도를 소진**해 오늘
안에 끝내지 못했다.

한도가 리셋된 뒤 아래를 실행하면 실패분 142건만 대상이 된다(`failed` 상태를 재조회
대상으로 잡는 규칙). `--force-details`는 쓰지 않는다 — 이미 채운 702건까지 다시
부른다.

```bash
cd backend
PLACE_SYNC_DETAIL_CONCURRENCY=1 python -m scripts.sync_places \
  --from-snapshot ../supabase/data/places_api_snapshot_20260810.csv
```

## 이번에 겪은 것 — 다음에 같은 작업을 할 때

`detailIntro2` 응답이 100~150ms로 빨라 **기본 동시성 5는 초당 40회를 넘긴다.**
TourAPI는 초당 한도와 일일 한도를 각각 다른 코드로 돌려준다.

| reasonCode | 의미 | 재시도 |
| --- | --- | --- |
| 23 | 초당 서비스 요청제한 초과 | 잠시 쉬면 성공한다 |
| 22 | 일일 서비스 요청제한 초과 | 오늘은 무의미하다 |

`place_sync`는 두 코드를 모두 `TOUR_DETAIL_RATE_LIMITED`로 뭉뚱그린다. 그래서 일일
한도에 걸린 뒤에도 호출당 최대 3회(본 시도 + 재시도 2회)를 계속 던졌고, 그만큼
한도를 더 빨리 태웠다. 실행 이력은 아래와 같다.

| 실행 | 동시성 | 대상 | 성공 | 실패 |
| --- | --- | --- | --- | --- |
| 1차 | 5 | 844 | 220 | 624 (초당 한도) |
| 탐침 | 1 | 50 | 50 | 0 |
| 2차 | 1 | 574 | 432 | 142 (초당 한도) |
| 3차 | 1 | 142 | 0 | 142 (일일 한도) |

동시성 1도 지속 부하에서는 초당 한도에 걸린다(2차에서 25% 실패). 50건 탐침이 깨끗해
"동시성만 낮추면 된다"고 판단했지만, 한도를 재기에 표본이 짧았다. 호출 간 간격을
두는 설정이 필요하다.
