# Scoring 버전 이력

`backend/app/domain/scoring.py`의 `SCORING_VERSION` 하나를 다룹니다.
**점수 산출에 영향을 주는 변경이 있을 때 올리는 값**이고, B의 LLMOps
Trace(`record_trace(scoring_version=...)`)에 문자열로 저장됩니다. 그래서 나중에
로그만 보고 **"이 추천이 어떤 규칙으로 계산됐는지"를 역추적**할 수 있습니다.
B는 값의 의미를 해석하지 않습니다(B-01 경계 원칙).

관리: **D (@rayquaza410)** · 최종 확인: 2026-09-17.

## 1. 현재 값

| 상수 | 위치 | 현재 값 |
| --- | --- | --- |
| `SCORING_VERSION` | `backend/app/domain/scoring.py` | `recommendation-scoring-1.10.0` |

## 2. 올리는 규칙

상수 **바로 위 주석**이 정본이고, 아래는 그 판단 기준입니다.
(위치: `grep -n "SCORING_VERSION = " backend/app/domain/scoring.py`)

| 상황 | 올리나 |
| --- | --- |
| Feature 키 추가·삭제, 가중치 값 변경, 판정표 변경 | **올린다** |
| 같은 입력에 다른 점수가 나온다 | **올린다** |
| 확장했지만 기존 경로 점수는 완전히 동일 | 올리지 않는다 |
| 프롬프트만 고침(추출 정확도 개선) | 올리지 않는다 — 입력이 바뀐 것이고 로직이 아니다 |
| 리팩터링·로깅·응답 필드 추가 | 올리지 않는다 |

등급은 semver를 따릅니다.

- **MINOR** — Feature 키 추가, 가중치 조립 방식 변경, 판정 규칙 변경.
  기존 호출부가 수정 없이 동작하면(응답에 기본값 `None` 필드 추가 등) MINOR입니다.
- **MAJOR** — 기존 호출부가 깨지는 계약 변경.
- **PATCH** — 순위가 뒤집히지 않는 수준의 계산 오차 수정.

애매하면 **실제로 돌려서 점수 차이를 확인한 뒤** 판단합니다.

> **단위 테스트 통과가 "순위가 바뀌었다"의 증거는 아닙니다.** `1.8.0`에서 거리 축을
> 뺐을 때 테스트 5건이 다 통과했지만 전부 `feature_scores`·`weights_used`만 봤고,
> 실제 데이터로는 상위 5곳이 **한 곳도 바뀌지 않았습니다**(정렬 타이브레이커가 그
> 자리를 메우고 있었습니다). 순위 영향 범위를 적을 때는 가중치 표가 아니라
> **실제 후보를 흘려 상위 N곳을 비교한 결과**를 근거로 쓰는 편이 안전합니다.

> 이 값은 다른 버전 상수와 **독립**입니다. 운영시간 파싱(`OPERATING_PARSER_VERSION`)이나
> 프롬프트(`_BASE_PROMPT_VERSION`)가 바뀌어도 점수 산출 규칙이 그대로면 올리지 않습니다.

**"순위 영향 범위"가 이 표의 핵심입니다.** 버전이 올랐어도 그 조건을 말하지 않은
요청의 점수는 이전과 동일합니다 — 추천 결과가 달라졌다고 의심할 때 먼저 이 칸을 봅니다.

**`1.7.0`은 D의 변경이 아니라 사후 반영입니다.** `1.6.0` 이후 `scoring.py`를 바꾼
커밋이 4건 있었는데 버전이 따라오지 않았습니다. 2026-09-03에 4건을 하나씩 재서
**2건이 순위를 바꾸는 것**으로 확인하고 한 번에 올렸습니다(A·C 협의 완료).

**`OPTIONAL_FEATURES`에 이름을 넣는 것만으로는 올릴 근거가 되지 않습니다.** 조립부
두 곳이 실재 여부로 거릅니다(`build_weights`는 `in set(requested)`,
`weights_for_feature_scores`는 `in feature_scores`). 올릴 근거는 그 키를
`feature_scores`에 **실제로 채우는 새 경로**입니다.

같은 일이 반복되지 않게 CI에 알림을 넣었습니다(`.github/workflows/ci.yml`의
`Scoring version notice`). **막지 않고 PR 파일에 경고만 답니다** — 위 표처럼 절반은
정당하게 안 올려도 되는 변경이라, 막으면 우회하게 됩니다.

`1.0.0`~`1.2.0`은 Feature 키 구성과 가중치 합계를 바꾸지 않았습니다. 응답 스키마도
기본값 `None` 필드 추가라 하위호환이고, 기존 호출부가 수정 없이 동작하므로 MAJOR가
아닙니다. `1.3.0`이 **Feature 키를 하나 늘린 첫 변경**입니다.

`1.1.0`은 **D가 아니라 C가 올렸습니다.** 파일은 D 영역이지만 실내외 Feature를 넣은 건
C였고, 상수 주석의 규칙대로 올려줬습니다. **D 영역 파일이라도 다른 사람이 이 값을 올릴
수 있습니다** — 그럴 때 3절에 행을 추가해 주시면 이력이 끊기지 않습니다.
