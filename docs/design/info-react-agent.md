# INFO 실시간 조회 ReAct 에이전트 전환 설계

- 작성일: 2026-09-02
- 상태: 구현·실측 완료, 기본값 off로 병합 대기 (PR #344)
- 관련 로드맵: [로드맵 24번](../roadmap.md#24-info-질의를-에이전트형-툴콜-루프로-전환--대화-이력-요약-압축-저장--아직-안-만듦)

## 1. 배경과 목표

지금까지 챗봇은 발화를 "이해"하는 것과 "행동"하는 것이 분리돼 있었다. LLM은
사용자 발화를 구조화된 값으로 뽑아내기만 하고("지금 서초동 주차 상황 알려줘"
→ `question_type=REALTIME_PARKING`, `place_name=서초동`), 그다음에 어떤 API를
몇 번 부를지는 코드가 고정된 분기로 정했다. 강의교재 90강에서 다룬
"에이전트/ReAct 패턴"(판단→행동→관찰→재판단을 LLM이 스스로 반복하는 방식)과는
거리가 있는 구조였다.

이 구조의 실제 문제는 서울시 실시간 데이터가 **닫힌 목록**이라는 데서
나왔다. 인구 데이터는 121개 지역, 상권 데이터는 82개 지역만 지원한다.
"서초동"처럼 이 목록 밖 지명을 물으면, 지금까지는 곧장 사용자에게 "검색
범위를 넓혀볼까요?"라고 되물었다. 실제 대화에서는 "교대쪽엔 없대. 그럼
강남역은?"처럼 한 번 더 물어봐야 했고, 사용자 입장에선 "그냥 알아서 근처로
찾아봐 주면 안 되나" 싶은 지점이었다.

목표는 이 판단(어디로, 몇 번 다시 조회할지)을 코드가 아니라 LLM이 직접
하도록 넘기는 것이다.

## 2. 왜 전면 전환이 아니라 INFO 실시간 조회부터인가

INFO 질문 유형마다 백엔드 응답 스키마(`EventInfoResult`,
`RealtimeCityInfoResult` 등)와 프론트엔드 카드가 1:1로 고정돼 있다. 이 계약
자체를 건드리는 건 중간 규모 이상의 작업이라, 처음부터 모든 인텐트를
바꾸는 대신 범위를 좁혔다.

**INFO의 실시간 조회(주차·지하철·버스·행사·교통·상권)만** 선택한 이유:

- 기존 계약(`fetch_info_context()`가 반환하는 응답 형태, 프론트 카드)을 그대로
  두고, 이 메서드를 "지역명만 바꿔서 여러 번 호출"하는 방식으로 감쌀 수 있다.
- "지원 지역 목록에 없음"이라는 실패가 명확하고 흔해서, 에이전트가 판단할
  대상이 뚜렷하다(추천 파이프라인처럼 "후보가 부족하지만 아예 없진 않다"
  같은 애매한 중간 상태가 없다).

스파이크 단계에서 실측한 결과, 재시도가 있는 경우도 2~3라운드에 2~3초
정도로 끝나 기존 파이프라인과 체감 속도 차이가 크지 않았다.

## 3. 핵심 결정 — 코드가 아니라 LLM에게 도구를 쥐여준다

기존 방식은 "지역 없음 → 곧장 되묻기"처럼 실패 케이스마다 코드가 분기를 짜야
했다. 이 설계는 대신 LLM에게 파이썬 함수 두 개를 도구로 준다.

- `get_realtime_population_data(place_name)`
- `get_realtime_commercial_data(place_name)`

그리고 Google Gemini의 **automatic function calling** 기능을 쓴다. LLM이
"이 지역명으로 도구를 불러봐야겠다"고 판단하면, SDK가 그 파이썬 함수를 대신
실행하고 결과를 다시 LLM에 보여준다 — 이 왕복을 최대 3번(`max_tool_calls=3`)
까지 반복하게 했다.

LLM에게 준 지시문의 핵심 규칙 세 가지:

1. 도구가 "이 지역은 없음"이라고 하면, 사용자에게 되묻지 말고 **근처의 잘
   알려진 다른 지역명**으로 스스로 다시 조회해본다.
2. 도구가 "여러 곳으로 해석된다"며 후보 목록을 주면(예: "강남"처럼 넓은
   지명), 그중 질문과 가장 관련 있어 보이는 곳(대표 지하철역·랜드마크)을
   스스로 골라 재조회한다.
3. 확인되지 않은 사실은 지어내지 않는다. 찾은 지역이 원래 물어본 곳과
   다르면 그 사실을 답변에 자연스럽게 밝힌다.

이 방식 덕분에 "이 지역이 없으면 어떻게 할지", "여러 후보 중 뭘 고를지"
같은 판단 로직을 코드로 하나하나 분기 짤 필요가 없어졌다 — 그 판단 자체를
LLM의 자연어 추론에 맡긴 것이 이 설계의 핵심이다.

## 4. 실제로 부딪힌 문제 세 가지

실제 Gemini/네이버/서울시 API로 붙여보며 코드만 봐서는 안 보였던 문제를
세 가지 발견했다.

**추적 ID 충돌.** 재시도할 때마다 원래 요청의 추적 ID(`request_id`)를 그대로
재사용했더니, 두 번째 시도의 기록이 첫 번째 시도와 충돌해 "시스템 오류"로
잘못 보고됐다. 재시도마다 새 추적 ID를 발급하도록 고쳤다.

**함수 타입 정보 유실.** 이 프로젝트 파이썬 파일 상단에는 관례적으로
`from __future__ import annotations`가 있는데, 이 설정이 있으면 함수의 타입
힌트가 실행 시점엔 전부 문자열로 취급된다. 그런데 automatic function calling은
그 타입 정보를 실제 타입으로 읽어야 도구 결과를 검증할 수 있어서, 타입이
문자열인 채로 있으면 내부적으로 오류가 났다(사용자에게는 그냥 "도구 호출
실패"로만 보였다). 도구로 넘기는 함수의 타입 힌트를 실행 시점에 다시
해석시켜주는 방식으로 고쳤다.

**빈 답변으로 끝나는 경우.** 도구 결과가 "없음"으로 끝난 뒤, LLM이 가끔 최종
답변 문장 없이 턴을 마치는 경우가 있었다(API 자체의 특성으로 보이며 완전히
막을 방법은 없었다). 이럴 때를 대비해, LLM이 빈 텍스트를 낸 경우에만 쓰는
별도의 정리된 안내 문장 생성기를 안전장치로 붙였다.

## 5. 비용 관점 — 몇 번을 더 부르는가

이 방식은 LLM 호출 자체는 여전히 1번(우리 코드가 부르는 횟수 기준)이지만,
그 안에서 Gemini 서버와 최대 3번까지 왕복할 수 있다. 왕복이 늘수록 이전
대화 전체(원 질문 + 도구 호출 기록 + 도구 결과)를 매번 다시 보내야 해서
입력 토큰도 늘어난다.

다만 실측 두 건(성공 1회 완료 케이스 vs 재시도 포함 케이스)의 토큰 수가
예상보다 비슷하게 나와, Gemini가 응답에 담아주는 토큰 집계 값이 전체 왕복을
합산한 것인지 마지막 왕복 한 번만의 것인지 아직 확실하지 않다. 이 부분은
검증되기 전까진 "지금 보이는 토큰·비용 수치는 최소치일 수 있다"고 보수적으로
가정해야 한다. 자세한 후속 검증 계획은 [로드맵 24번](../roadmap.md)에 남겨뒀다.

## 6. 기본값 off로 두는 이유

`agentic_realtime_info` 설정 하나로 켜고 끌 수 있게 했고, 기본값은
`False`다(기존 `use_langgraph_pipeline` 플래그와 같은 패턴). 아직 팀 협의
전 실험 단계이고, LLM이 스스로 재시도·지역 선택을 판단하는 만큼 코드로 정해둔
고정 분기보다 결과 예측이 어렵다는 특성이 있어, 문제가 보이면 이 값 하나로
바로 기존 경로(고정 분기, 되묻기)로 되돌릴 수 있게 해뒀다.

## 7. 다음에 이 방식을 넓힐 때 참고할 점

- 이번엔 응답 스키마가 고정된 INFO 실시간 조회만 다뤘다. 추천(RECOMMEND)이나
  다른 INFO 유형까지 넓히려면 각 응답 스키마·프론트 카드 계약을 어떻게
  유지할지부터 다시 설계해야 한다.
- 토큰 집계 방식(5절)은 왕복이 잦아질수록 오차가 커질 수 있는 문제라, 범위를
  넓히기 전에 먼저 확인하는 게 안전하다.
- 프롬프트(LLM 지시문)는 지금 코드에 인라인 문자열로 있다. 이 방식이 팀
  검토를 거쳐 채택되면, 다른 인텐트 프롬프트처럼 정식 자산(Markdown +
  meta.yaml)으로 옮기는 작업이 뒤따라야 한다.
