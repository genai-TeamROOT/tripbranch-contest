# 장소 분위기 임베딩 설계 v0.1

장소 사진을 벡터로 만들어 두고 두 가지에 쓴다 — 발화에서 뽑은 분위기로 추천 순위를
다듬는 것(축)과, 사용자가 올린 사진과 닮은 곳을 찾는 것(사진 검색)이다.

이 문서는 **지금 어떻게 동작하고 무엇을 해야 하는가**를 적는다. 왜 이 모델·이 축인지를
고른 과정과 측정 기록은 저장소 밖 연구 기록에 있고, 결론만 `docs/decision-log.md`의
D-082·D-087·D-094·D-115에 남아 있다.

## 1. 두 경로

한 벌의 벡터를 쓰지만 읽는 방식이 다르다.

```text
발화 경로   "조용한 데" → 미리 정한 축 이름 → axis_scores 조회 → 추천 채점에 반영
사진 경로   사진 업로드 → SigLIP 인코딩 → 장소 벡터와 최근접 검색 → 상위 N곳
```

| | 발화 경로 | 사진 경로 |
| --- | --- | --- |
| 읽는 값 | `axis_scores` (미리 계산됨) | `embedding` (실행 시 비교) |
| 모델이 서버에 필요한가 | 아니오 | **예** (SigLIP 상주) |
| 추천 채점을 타는가 | 예 | 아니오 — 사진 유사도만으로 줄 세운다 |
| 평균 빼기 | 적용하지 않는다 | **적용한다** (D-115) |

**사진 경로가 축을 쓰지 않는 것이 요점이다.** 벡터를 통째로 비교하므로 축이 가르는
차원(낡음·한산함 같은 것)이 "이것이 무슨 장면인가"라는 큰 신호에 묻힌다. 그래서 사진
경로에만 평균 빼기가 붙는다(3절).

## 2. 테이블

```text
place_image_embeddings   사진 한 장 = 한 행. 원본 주소와 벡터
        ↓ 장소별 평균
place_mood_vectors       장소 한 곳 = 한 행. 평균 벡터 + 축 점수 + 사진 수
        ↓ 전체 평균
place_mood_center        한 행뿐. 사진 검색에서 빼는 중심 벡터
```

| 테이블 | 무엇이 한 행인가 | 주요 컬럼 |
| --- | --- | --- |
| `place_image_embeddings` | 사진 한 장 | `content_id`, `photo_order`, `origin_url`, `embedding vector(768)` |
| `place_mood_vectors` | 장소 한 곳 | `content_id`, `embedding`, `axis_scores jsonb`, `photo_count`, `anchors_version` |
| `place_mood_center` | 전체에 하나 | `embedding`, `place_count`, `updated_at` |

모델은 `google/siglip2-base-patch16-224`이고 768차원, 길이 1로 정규화해 넣는다.
**질의도 같은 모델·같은 정규화여야 한다** — 다르면 오류 없이 엉뚱한 순위가 나온다.

`photo_count`가 1인 장소는 `detailImage2`가 비어 대표 이미지 한 장으로 대체된
곳이다(D-087). 그 한 장이 장소 벡터를 통째로 좌우하므로 API 응답에 그대로 실어
화면이 신뢰도를 낮춰 보일 수 있게 한다.

`anchors_version`은 축 정의의 해시다. 축 문구나 목록이 바뀌면 값이 달라지므로,
섞인 버전이 있는지는 이 컬럼을 세어 확인한다.

## 3. 평균 빼기 (D-115)

사진 검색은 질의와 장소 벡터에서 각각 **전체 평균을 빼고** 비교한다.

```text
지금   질의 · 장소벡터
실제   (질의 − 중심) · (장소벡터 − 중심)
```

5,465개 단위벡터의 평균 길이가 0.80이다 — 거의 같은 방향을 보고 있다는 뜻이고, 그
공통 성분이 분위기 차이를 덮고 있었다. 사람 눈가림 채점에서 48.2% → 53.2%였고, 실제
사용 조건인 직접 찍은 사진에서 44.3% → 51.9%로 더 컸다.

**유의성은 경계에 걸쳐 있다**(`p = 0.0481` / `0.0730` / `0.0812`). 질의가 28장뿐이라
표본을 늘려 다시 봐야 한다. 그럼에도 켜 둔 것은 방향이 세 시험에서 모두 같고, 나빠진
지표가 없으며, 되돌리는 비용이 설정 하나이기 때문이다.

**중심은 테이블에 저장해 둔다.** 매 요청마다 `avg()`로 구하면 1,314ms가 더 붙는다.
저장해 두면 조회가 125ms다(6,830곳, 빼지 않을 때 147ms). 전체를 훑는 구조이며
자세한 것은 4절 끝의 색인 이야기에 있다.

**축 점수에는 적용하지 않는다.** 축 점수는 이미 계산돼 `axis_scores`에 들어 있고,
축 점수는 방향과의 내적이라 중심을 빼면 값의 의미가 달라진다.

### 유사도 눈금이 달라진다

공통 성분이 빠져 `similarity`가 전반적으로 낮아진다. **켠 결과와 끈 결과의 숫자를
직접 견주면 안 된다.** 관측 요약(`place_mood_photo_search` span)에 `mean_center`를
함께 싣는 이유가 이것이다 — 두 눈금을 섞어 보면 컷값을 엉뚱하게 잡는다.

애초에 유사도는 순위를 위한 값이지 "얼마나 닮았다"의 눈금이 아니다. 컷을 재지 못해
지금은 컷 없이 상위 N곳을 그대로 준다(D-094). 화면에 백분율로 표시하지 않는다.

## 4. 적재 절차

임베딩은 서버가 아니라 코랩에서 만든다. 구 단위로 돈다.

```text
1. 사진 수집        TourAPI detailImage2 (오퍼레이션 단위 일일 1,000회)
2. 코랩에서 인코딩   {구}_manifest.json + {구}_image_vectors.npy
3. 적재             python -m scripts.import_mood_embeddings --batch <구>
4. 색인             HNSW를 만든다 (대량 적재 뒤에)
5. 중심 갱신        select refresh_place_mood_center();
```

**4번과 5번을 빠뜨리기 쉽다.**

- HNSW는 **대량 적재가 끝난 뒤에** 만든다(D-082·D-087). 먼저 만들어 두고 밀어 넣으면
  적재가 크게 느려진다. 다만 지금은 그 색인을 조회가 쓰지 못한다 — 아래 참고.
- 중심을 갱신하지 않으면 옛 표본의 중심으로 계속 검색한다. **오류가 나지 않는다** —
  결과는 그럴듯하게 나오고 조금씩 나빠질 뿐이다. `place_mood_center.place_count`를
  실제 장소 수와 비교하면 누락을 잡을 수 있다.

중심이 아예 없는 상태에서 평균 빼기를 켜면 RPC가 예외를 던진다. 조용히 빼지 않은
결과를 주면 켠 줄 알고 쓰는데 실제로는 옛 순위라, 왜 좋아지지 않는지 추적할 수 없다.

### HNSW 색인은 걸려 있지만 지금 조회는 쓰지 못한다

`place_mood_vectors_embedding_hnsw_idx`가 있고 잘 동작한다. 테이블을 직접 정렬하면
전체를 훑는 것보다 **100배 넘게** 빠르다.

```
색인을 타는 조회                      1ms    (테이블을 직접 정렬할 때)
search_place_mood · 평균 빼기 끔    147ms
search_place_mood · 평균 빼기 켬    125ms   ← 지금 사진 검색이 하는 일
```

6,830곳 기준 10회 평균이다. **평균을 빼는 쪽이 느리지 않다** — 뺄셈이 붙는데도
그렇다. 원본 벡터는 서로 방향이 비슷해(중심과 0.80) 거리 값이 촘촘한 반면 뺀
뒤에는 흩어져, 상위 5개를 고르는 동안 일찍 걸러지는 것으로 보인다. 확인한 설명은
아니고 관찰이다.

**그런데 `search_place_mood`는 색인을 타지 못한다.** 막는 이유가 둘이고, 둘 다
독립적이다.

1. **조회문 모양.** 반경·활성 여부로 걸러야 해서 `places`와 조인하고 CTE로 감쌌다.
   색인은 테이블 컬럼을 직접 `order by`할 때만 쓸 수 있어, CTE 결과를 정렬하는
   지금 모양으로는 탈 수 없다. 평균 빼기를 끄고 재도 147ms로 전부 훑는다.
2. **평균 빼기.** 색인은 원본 벡터로 엮였는데 질의는 `(원본 − 중심)`의 거리를
   묻는다. 뺀 뒤는 다른 공간이라 미리 엮어 둔 그래프가 맞지 않는다.

1번만 고쳐도 2번이 남으므로 소용이 없다.

**그래도 색인을 떼지 않았다.** 지금 규모에서 유지 비용이 작고, 뗐다가 다시 만드는
것도 일이다. 적재가 답답해지면 그때 정한다.

**나중에 정말 빠르게 하려면 색인이 아니라 컬럼이 필요하다.** 미리 뺀 벡터를 별도
컬럼에 두고 거기에 HNSW를 걸면 다시 1ms 대로 돌아온다. 지금 그렇게 하지 않은 것은
원본과 두 벌이 되어 적재 때마다 어긋날 수 있기 때문이다 — 중심이 바뀌면 전체를
다시 계산해야 한다.

전체를 훑으므로 응답이 장소 수를 따라 늘기는 한다. 다만 **아직 병목이 아니다** —
끝단 응답이 516ms(중앙값, 6,830곳)인데 그중 DB가 125ms고 나머지 390ms는 SigLIP
인코딩·상세 조회·하드 필터다. 장소를 5,465곳에서 6,830곳으로 25% 늘렸을 때 끝단은
433ms에서 516ms로 움직였다.

**컬럼을 만들 때는 DB가 끝단에서 눈에 띄는 몫이 되는 시점이다.** 지금은 아니다.

첫 요청은 캐시가 식어 있어 훨씬 느리다 — 대량 적재 직후 1,558ms를 봤고, 두 번째
요청부터 125ms였다. 배포 직후나 오래 쉰 뒤의 첫 요청은 이 값을 감안한다.

## 5. 설정

| 키 | 기본값 | 무엇 |
| --- | --- | --- |
| `PLACE_MOOD_ENABLED` | `false` | 두 경로를 함께 켜고 끈다 |
| `PLACE_MOOD_WARMUP_ENABLED` | `false` | 기동 때 SigLIP을 미리 올린다 |
| `PLACE_MOOD_MEAN_CENTER_ENABLED` | `true` | 사진 검색에서 평균을 뺀다(D-115) |

`PLACE_MOOD_ENABLED`가 꺼져 있으면 나머지 둘은 무시된다.

SigLIP은 선택 의존성이다(`pip install -e ".[mood]"`). 설치돼 있지 않으면 **발화
경로만 돈다** — 축 점수는 모델 없이 읽을 수 있기 때문이다. 사진 경로만 못 쓰고,
Provider가 `photo_search_available`로 알린다.

RPC의 `p_mean_center` 기본값은 `false`다. 켜고 끄는 판단은 설정이 한다 — DB 함수가
스스로 켜면 설정을 꺼도 안 꺼지는 경로가 생긴다.

## 6. 사진 검색 요청의 흐름

```text
POST /api/places/similar-by-photo   (multipart)
  → 위치 해석      대화가 잡은 기준점을 이어받는다
  → 사진 순위      search_place_mood RPC — 반경 안 전부를 줄 세운다
  → 상위 N곳 상세  DB에서 배치로 읽는다
  → 하드 필터      prepare_recommendation_from_context()
```

**추천과 순서가 반대다.** 추천은 후보를 먼저 모으고 채점하지만, 사진 검색은 먼저 줄을
세우고 상위 N곳만 상세를 확인한다. 사진 유사도는 DB 안에서 끝나 사실상 공짜인데
상세 조회는 비싸기 때문이다. 순서를 뒤집기 전에는 후보 상한에 걸려 어떤 사진을 올려도
같은 대여섯 곳이 순서만 바뀌었다.

하드 필터 판정은 직접 하지 않고 추천과 같은 함수를 태운다. 영업시간 해석을 여기서
새로 만들면 같은 장소가 추천에서는 열렸는데 사진 검색에서는 닫힌 것으로 갈릴 수 있다.

날씨는 조회하지 않는다. 하드 필터는 영업시간·이미 본 곳·거절한 곳만 보고, 사진 검색은
채점을 타지 않아 날씨를 쓸 데가 없다.

## 7. 정하지 못한 것

- **유사도 컷.** 사진끼리의 "이 정도면 닮았다" 경계를 재지 못했다. 상관이 `r = +0.127`로
  약하고, 0.78에서 자르면 정확도 8.5%p를 얻는 대신 결과의 28%를 잃어 손해였다.
- **사진 한 장짜리를 피하는 것.** DB의 56%가 한 장짜리인데 결과에는 5%만 나왔다.
  평균 빼기로 15%까지 올랐고, 새로 들어온 한 장짜리는 오히려 잘 맞았다(14칸 중
  9칸이 "비슷하다"). 피하는 것이 손해라는 쪽이지만 표본이 14건이다.
- **평균 빼기의 표본.** 질의 28장에서 유의성이 0.05 언저리다(D-115). 다음 측정 때는
  질의를 새로 마련해야 한다 — 지금 홍보 사진 질의 12장이 강남 것이라, 강남을
  적재하면 그 사진들이 자기 자신을 1위로 찾게 되어 못 쓴다.
- **사진별 최고점 방식.** 장소 평균 대신 사진 하나하나와 비교해 장소별 최고점을 쓰면
  평균 편향이 사라진다. 조회 구조가 통째로 바뀌므로 별건으로 남겼다.
- **1위는 평균 빼기로 나아지지 않았다**(67.9% → 67.9%). 2~5위만 개선됐다.
