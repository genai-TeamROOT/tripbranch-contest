# 멀티턴: 트리비가 대화 맥락을 어떻게 이어가는가

| 항목 | 값 |
|------|-----|
| 상태 | 구현 완료, 실 API로 검증됨 |
| 최종 수정 | 2026-08-31 |
| 관련 문서 | [conversational-layer.md](conversational-layer.md) — 대화 이력 저장소(`recent_turns`)를 처음 만든 문서. 이 문서는 그 저장소를 실제로 판단에 쓰기까지의 이야기다 |

## 0. 왜 이 문서를 쓰는가

"안국역 혼잡도 알려줘" 다음에 "인사동은?"이라고 물으면, 사람이라면 당연히 "인사동
혼잡도"를 묻는 거라고 알아듣는다. 그런데 트리비는 최근까지 이걸 못 알아듣고 엉뚱하게
"인사동 근처 장소 추천"으로 대답했다. "친구들이랑 갈거야"라고 조건을 말해도, 뒤이어
나오는 답변 문장은 "혼자서도 가기 좋고"라고 말하는 일도 있었다.

두 문제 모두 겉으로는 "멀티턴이 안 된다"처럼 보이지만, 원인은 서로 다르다. 이 문서는
**우리 멀티턴이 지금 정확히 어떤 방식으로 동작하는지**, 그리고 **왜 이런 문제가 있었고
어떻게 고쳤는지**를 팀원이 코드를 안 봐도 이해할 수 있게 정리한다.

---

## 1. 멀티턴의 표준 개념 — 우리는 뭘 따르고 뭘 다르게 했나

LLM은 호출 하나하나가 완전히 독립적이다. 아무것도 기억하지 못한다. "대화가 이어지는
것처럼 느껴지게" 하려면, **호출하는 쪽(우리 서버)이 지난 대화를 매번 다시 챙겨서
같이 보내야 한다.** 이게 멀티턴의 전부다.

표준적인 방식(강의교재 기준)은 이렇다.

```
사용자 입력
→ 이력에 user로 추가
→ (대화가 길면) 최근 N턴만 추리거나 오래된 건 요약
→ LLM 호출 — 이력 전체를 같이 보냄
→ LLM 답을 이력에 model로 추가
→ 세션별로 저장(DB/Redis)
```

우리도 이 뼈대를 그대로 따른다. 다른 점은 하나뿐이다 — **model 쪽(트리비 답변)을
이력에 넣을 때, 답변 문장 원문 하나만 넣는 게 아니라 "그 턴을 어떻게 처리했는지"도
같이 넣는다.**

```
표준:   model 이력 = "인사동은 조선시대부터 이어진 전통 거리예요..."
우리:   model 이력 = "인사동은 조선시대부터 이어진 전통 거리예요...
                      (처리 기록 — 처리 의도: INFO; 질문 유형: concentration)"
```

이렇게 하는 이유는 뒤(4장)에서 설명한다.

## 2. 저장 — 무엇을, 어디에, 얼마나

**저장 위치**: 세션 상태 테이블(`agent_states`)의 `recent_turns` 칼럼 하나.
사용자 한 명의 대화 하나 = 세션 하나. 30분 안 쓰면 세션이 만료되며 같이 사라진다.

**턴 하나에 담기는 것**:

| 필드 | 내용 | 비고 |
|---|---|---|
| `user_input` | 사용자가 친 문장 원문 | 최대 300자, 넘으면 뒤를 자름 |
| `assistant_message` | 트리비가 실제로 답한 문장 원문 | 최대 300자. 과거 세션엔 없을 수 있음(None) |
| `intent` | 그 턴을 어떤 인텐트로 처리했나 | 예: `INFO`, `RECOMMEND` |
| `question_type` | INFO였다면 무슨 질문이었나 | 예: `concentration`(혼잡도) |
| `place_names` | 화면에 보여준 장소 이름들 | "거기" 같은 지시어 해석에 씀 |
| `offered_action` | 트리비가 먼저 제안한 게 있었다면 그 id | 상황 제안 기능(대화층 4단계)용 |

**보관 범위**: 최근 **5턴만**. 6턴째가 들어오면 가장 오래된 턴이 밀려난다(슬라이딩
윈도우). 5턴 밖으로 나간 정보는 원문으로는 더 이상 안 남지만, 완전히 사라지는 건
아니다 — 3장에서 설명하는 "누적 조건"이 따로 그 역할을 한다.

---

## 3. 판단 — 저장한 이력을 실제로 어떻게 쓰는가

여기서부터가 이번에 정리한 부분이다. 우리는 판단을 **두 갈래**로 나눠서 쓴다.

### 갈래 1 — "대화 흐름을 읽어야 아는 것"은 이력을 그대로 보여주고 LLM이 판단

예: "인사동은?"이 방금 물어본 혼잡도 질문의 후속인지, 아니면 완전히 새 질문인지.
이건 숫자로 딱 떨어지는 규칙을 만들기 어렵다 — 사람도 문맥을 보고 판단하는 영역이다.

그래서 이런 경우는 **최근 대화 원문을 LLM에게 그대로 보여주고**, "생략된 짧은 후속
발화는 직전 턴과 같은 종류의 질문으로 봐라" 같은 사용법 지침 한 장(`_shared/rules/
conversation_history.md`)만 던져준 뒤 LLM이 알아서 판단하게 한다. 인텐트를 정하는
6단계(분류, RECOMMEND/MODIFY/INFO/COMPARE/GENERAL 조건 추출) 전부 이 이력을 받는다.

### 갈래 2 — "숫자·상태로 정해지는 것"은 여전히 코드가 정한 규칙을 쓴다

예: "다른 곳 보여줘"는 이전에 추천을 이미 받은 상태에서만 "다른 곳"이라는 뜻이 성립한다.
추천을 한 번도 안 받았으면 그냥 새 추천 요청이다. 이런 건 대화를 아무리 잘 읽어도 LLM
혼자서는 답을 낼 수 없다 — **서버가 "지금 추천을 몇 개나 보여줬는지"를 정확히 세서
알려줘야** 한다.

이런 규칙은 지금 라우터 프롬프트에 21개 정도 명시적으로 박혀 있다(`router/
context_rules.md`, `router/boundary_cases.md`). "이전 추천 있음/없음", "직전 턴이
되묻는 중이었는지" 같은 상태값을 서버가 계산해서 프롬프트에 문장으로 박아둔 것들이다.
이건 갈래 1로 대체할 수 있는 게 아니라서 그대로 둔다.

### 이번에 실제로 있었던 문제 — 두 갈래가 섞여서 생긴 일

"안국역 혼잡도 알려줘" → "인사동은?" 문제는 사실 **갈래 2의 규칙이 갈래 1을 눌러버린
것**이었다. "이전 추천 있음 + 지명 단독 → MODIFY(위치만 바꿔서 추천)"라는 코드 규칙이
너무 강하게 박혀 있어서, "방금 정보 질문 중이었다"는 맥락을 LLM이 참고할 수 있는
지침 자체가 없었다. 그래서 갈래 2 규칙에 "단, 방금 INFO 질문 중이었으면 그 흐름을
우선한다"는 예외를 한 줄 추가했다(21개 중 딱 이 하나만).

## 4. 답변을 "쓸 때"도 맥락을 봐야 한다

여기가 가장 놓치기 쉬운 부분이다. "무엇을 할지 판단하는 단계"와 "실제로 사용자에게
보여줄 문장을 쓰는 단계"는 **서로 다른 LLM 호출**이다.

```
1단계: 판단   "친구들이랑 갈거야" → MODIFY, companion=friend  (조건 추출 성공)
2단계: 실행   D(추천 엔진)가 조건에 맞는 장소 5곳을 골라낸다
3단계: 서술   "말풍선에 뭐라고 쓸까?" ← 이 단계가 문제였다
```

1단계가 `companion=friend`를 정확히 뽑아냈어도, **3단계(말풍선 문장 생성)가 그 값을
아예 받지 않는 구조**였다. 3단계는 그동안 카드 데이터(장소명·거리·운영시간)만 보고
문장을 썼기 때문에, 동행 정보를 몰라서 "혼자서도 가기 좋고"처럼 엉뚱한 톤으로 쓴 것이다.

고친 방법: 3단계에 "지금까지 사용자가 말한 조건"(`UserConditions`)을 함께 건네고,
"사실은 카드에서만, 말투·강조점은 조건에서 고르라"는 규칙을 추가했다. 대화 원문
5턴이 아니라 **누적 조건**을 쓴 이유는, 조건은 5턴 창 밖으로 밀려나도 계속 살아있기
때문이다 — "3턴 전에 친구랑 간다고 했었지"도 이 값으로 커버된다.

같은 이유로 GENERAL·COMPARE 같은 답변 생성 단계에도 최근 대화 이력을 함께 넘기도록
넓혔다. 답변을 "쓰는" 6개 지점(추천 요약, GENERAL 답변, INFO 답변, COMPARE 요약과
그 스트리밍 버전들) 전부 해당한다.

## 5. 한눈에 보는 전체 흐름

```
사용자: "안국역 혼잡도 알려줘"
  ├─ 1단계 판단: INFO, question_type=concentration, place=안국역
  ├─ 2단계 실행: 안국역 혼잡도 조회
  ├─ 3단계 서술: "안국역은 현재 여유로워요..."
  └─ 저장: recent_turns에 이번 턴 추가
       user_input="안국역 혼잡도 알려줘"
       assistant_message="안국역은 현재 여유로워요..."
       intent=INFO, question_type=concentration, place_names=[안국역]

사용자: "인사동은?"
  ├─ 1단계 판단: 최근 대화(위 턴)를 함께 봄
  │    → "지명만 던진 짧은 후속 질문" 패턴 인식
  │    → 직전과 같은 질문 종류(concentration)를 이어받음
  │    → INFO, question_type=concentration, place=인사동  ✅
  ├─ 2단계 실행: 인사동 혼잡도 조회
  ├─ 3단계 서술: "인사동은 현재..."
  └─ 저장: 다시 recent_turns에 추가 (최대 5턴 유지)
```

## 6. 한계와 앞으로 할 일

- **21개 남은 하드코딩 규칙**은 이번에 손대지 않았다. 대부분 "숫자·상태로 정해지는"
  갈래 2에 속해 계속 필요할 가능성이 높지만, 새 버그가 나올 때마다 그 규칙 하나만
  떼어내 실측하고 지우는 식으로 점진적으로 정리할 예정이다(한 번에 다 지우면 뭐가
  깨질지 알 수 없다).
- **5턴을 벗어난 대화 원문은 진짜로 사라진다.** 누적 조건(`UserConditions`)이 그 공백을
  일부 메우지만, "3턴 전에 이런 이야기를 했었지" 같은 순수 잡담 맥락까지는 못 살린다.
- **처리 기록 문구가 답변에 그대로 새어나갈 위험**은 이력 사용법 지침에서 "그건
  사용자에게 보인 말이 아니니 인용하지 마라"고 명시해 막아뒀지만, 결국 LLM의 준수에
  기대는 부분이라 완전한 보장은 아니다.
