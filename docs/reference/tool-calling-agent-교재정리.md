# 강의교재 정리 — 도구 호출(24강) / 에이전트(90강)와 우리 챗봇 비교

출처: `docs/reference/강의교재_본문전처리_1강-94강.csv` (제24강 `24-1`~`24-8`, 제90강 `90-1`~`90-8`)

## 제24강 — 도구 호출(Function Calling)

- **문제**: LLM은 학습 시점 지식만 알아서 "지금 재고 있어요?" 같은 실시간·사내 데이터는 원천적으로 모른다. 프롬프트를 아무리 잘 짜도 못 고치는 영역.
- **발상**: 사람 상담사가 재고 조회 시스템을 열어보듯, LLM에게도 "필요하면 이 함수를 써"라고 도구를 쥐여준다.
- **핵심 오해 정정**: 모델은 함수를 직접 실행하지 않는다. 모델이 하는 일은 "이 함수를, 이 인자로 불러 달라"고 요청하는 것까지고, 실제 실행은 우리 코드가 한다.
- **동작 4단계**: ① 도구 선언 → ② 모델이 호출 요청(function_call) → ③ 우리 코드가 실행 후 결과(function_response) 전달 → ④ 모델이 결과를 받아 최종 답 작성.
- **자동/수동 모드**: 자동 모드는 SDK가 ②③을 알아서 처리(google-genai의 automatic function calling), 수동 모드는 ②에서 멈춰 우리가 직접 실행해야 함.
- 여러 함수를 이어서 부르는 "멀티스텝"도 가능하지만, 24강 시점에서는 기본적으로 **1회성 호출** 개념 위주.

## 제90강 — 에이전트(Tool Routing Agent)

- **문제의식**: 61강에서 사람이 직접 짠 `if-else` 라우팅(`route()` 함수)은 기능이 늘수록 elif가 끝없이 늘고, 키워드 매칭이라 표현 변화에 약해진다.
- **해법**: 라우팅 판단 자체를 LLM에게 넘긴다 — 분류기·RAG·요약 같은 기능들을 "도구(tool)"로 등록해두면, LLM 에이전트가 사용자 말을 보고 알맞은 도구를 스스로 골라 호출.
- **정의**: "에이전트 = 생각 → 도구 호출 → 결과 관찰 → 다시 생각을, 목표를 이룰 때까지 스스로 반복하는 LLM" = **ReAct(Reason+Act) 패턴**. `create_agent(model, tools=[...])`(LangChain v1 + LangGraph)가 이 반복 루프를 미리 짜둔 완제품.
- **24강과의 관계**: 24강 function calling이 보통 1회성 호출이라면, 90강 에이전트는 그걸 "목표 달성까지 자동 반복"으로 확장한 것.
- **설계의 핵심**: 라우팅 규칙이 사람의 `if-else` 코드에서 **도구의 docstring**으로 옮겨간다. `@tool` 데코레이터를 붙이면 함수 이름+타입힌트+docstring이 그대로 LLM에게 전달되는 "도구 사용설명서"가 되고, docstring을 잘 쓰는 게 설계의 9할.
- **안전장치**: 도구를 무한정 부를 위험이 있어 `recursion_limit` 같은 반복 횟수 제한을 둔다.

## 우리 챗봇과의 차이점

| | 교재 24강 (function calling) | 교재 90강 (에이전트) | 우리 챗봇 |
|---|---|---|---|
| 호출 방식 | 보통 1회성 도구 호출 | 목표 달성까지 자동 반복(ReAct 루프) | `backend/app/providers/protocols.py`의 `answer_with_tools()` — "LLM이 tools를 몇 번이든(최대 max_tool_calls회) 스스로 골라 호출"한다고 docstring에 90강 ReAct를 명시적으로 인용 |
| 실제 구현체 | google-genai automatic function calling | `create_agent`(LangChain v1 + LangGraph) | `backend/app/providers/gemini.py`의 `GeminiProvider.answer_with_tools` — Gemini SDK의 `automatic_function_calling` 옵션을 그대로 사용(LangChain `create_agent`는 안 씀) |
| 적용 범위 | 예시 위주(재고/주문 조회) | 분류기·RAG·요약을 전부 도구로 묶은 범용 에이전트 | **INFO(실시간 인구/상권 조회) 한 슬라이스에만** 적용(`agent_runtime.py`의 `_fetch_realtime_info_agentic()`), 그것도 기능 플래그 `agentic_realtime_info` 기본값 `False`로 아직 실서비스에는 꺼져 있음 |
| 라우팅 방식 | — | LLM이 도구 docstring 보고 스스로 판단 | RECOMMEND 등 대부분 파이프라인은 여전히 **LangGraph 기반 고정 라우팅 그래프**(`graph/` 디렉터리) — 즉 61강식 "사람이 정한 분기"에 더 가깝고, 90강처럼 LLM이 전체 기능 중 도구를 자유롭게 고르는 범용 에이전트는 아님 |
| 자기 교정 | 없음 | LLM이 스스로 재시도 판단 | INFO 슬라이스에서는 "지원 지역 아니면 다른 지역명으로 재조회해보라"는 지시를 도구 docstring에 직접 넣어 LLM이 스스로 재시도하게 설계 — 90강 "docstring=라우팅 규칙" 통찰을 그대로 반영. RECOMMEND의 재시도(`tool_fetch → widen_search_retry`)는 이와 별개로 **코드가 정한 고정 재시도**라 에이전트형이 아님(로드맵에서 명확히 구분해둠) |

**한 줄 요약**: 교재는 24강(1회성 도구 호출) → 90강(LLM이 여러 도구 중 스스로 골라 반복 호출하는 범용 에이전트)으로 개념이 확장되는데, 우리 챗봇은 이 스펙트럼의 중간 지점 — "여러 기능을 스스로 고르는" 90강형 범용 에이전트는 아직 없고, INFO 실시간 조회 한 곳에만 "같은 도구를 필요하면 재시도하는" 좁은 ReAct 루프를 적용해뒀으며 나머지는 여전히 사람이 짠 LangGraph 고정 라우팅입니다.

## 부록 — 에이전트형 전환이 목표일 때, INFO·이동수단은 지금 어느 방향으로 가고 있나

전제: 우리는 "언젠가 검토"가 아니라 **에이전트형 전환 자체가 목표**다. 다만 지금 코드에 있는 두 가지 사례(INFO 실시간 조회, 이동수단 판단)가 서로 다른 단계에 있어서, 그 차이가 "가야 할 방향"인지 "아직 안 간 것"인지가 헷갈릴 수 있다. 아래는 두 사례가 실제로 어떻게 구현돼 있는지와, 거기서 갈리는 두 갈래 방향(넓혀가기 vs 한 번에 통합)의 실질적 차이를 정리한 것.

### 이동수단 판단 — 아직 24강(구조화 출력) 단계

이동수단(교통수단) 판정은 `backend/app/tools/mode_judge.py`의 `LlmModeJudge.judge()` → `gemini.py`의 `judge_travel_modes()`로 이어지는데, 이는 90강식 "LLM이 도구를 몇 번이든 스스로 골라 호출"하는 루프가 아니라 **구조화 출력(structured output) 1회 호출**이다.

- `gemini.py`의 `_TravelModePlan(BaseModel)` — 구간별 이동수단 리스트를 스키마로 강제해서 한 번에 받음. 개수 검증은 호출부(`tools/schedule_travel.py::select_modes_for_segments()`)가 담당.
- `judge_travel_modes()`는 `thinking_budget=0`으로 호출 — "판정 근거(거리·도보시간·조건)를 프롬프트에 이미 명시적으로 주고 있어 thinking 없이도 고를 수 있고, 이 호출은 SCHEDULE·RECOMMEND 턴의 지연에 그대로 더해진다"는 주석대로, 왕복을 늘리지 않는 방향으로 설계됨.
- `build_mode_judge_instruction()`은 "특정 Intent에 매이지 않는다 — 일정 편성(SCHEDULE)과 추천(RECOMMEND)이 같은 판정을 쓴다"는 재사용 설계.

즉 이동수단 판단은 LLM이 "몇 번 부를지·무엇을 부를지"를 스스로 정하는 구간이 없다. 코드가 한 번 부르는 시점과 입력을 다 정해두고, LLM은 그 안에서 분류만 한다. 에이전트형으로 가려면 이 지점도 결국 손을 대야 하는 후보지만, 지금은 그 전환이 일어나지 않은 상태.

### INFO 실시간 조회 — 90강(ReAct 루프)까지 간 유일한 사례

`agent_runtime.py`의 `_fetch_realtime_info_agentic()`는 `answer_with_tools()`로 LLM이 지역명을 바꿔가며 최대 3번까지 스스로 재조회하게 만든, 이 저장소에서 유일하게 90강 패턴을 실제로 적용한 곳이다. `docs/design/info-react-agent.md`가 왜 여기부터 시작했는지 밝힌다.

> "INFO 질문 유형마다 백엔드 응답 스키마(`EventInfoResult`, `RealtimeCityInfoResult` 등)와 프론트엔드 카드가 1:1로 고정돼 있다. ... '지원 지역 목록에 없음'이라는 실패가 명확하고 흔해서, 에이전트가 판단할 대상이 뚜렷하다(추천 파이프라인처럼 '후보가 부족하지만 아예 없진 않다' 같은 애매한 중간 상태가 없다)."

즉 INFO가 먼저 간 이유는 "여기가 제일 안전해서"라기보다 "여기가 LLM이 판단할 것과 코드가 보장해야 할 것의 경계가 가장 뚜렷해서"에 가깝다. 실패 조건이 애매한 영역(RECOMMEND처럼 "후보가 적지만 0은 아님")은 LLM에게 판단을 넘겼을 때 언제 멈춰야 하는지가 불분명해진다.

### 방향이 갈리는 지점 — "넓혀가기" vs "한 번에 통합"

에이전트형 전환에는 실제로 두 갈래 방향이 있고, 지금 코드는 그중 하나(넓혀가기)의 첫걸음만 뗀 상태다.

**방향 A — 슬라이스별로 넓혀가기 (지금 INFO가 서 있는 자리)**
- 응답 스키마·프론트 카드 계약이 인텐트마다 다르게 고정돼 있는 지금 구조를 유지한 채, "LLM이 판단할 실패 조건이 뚜렷한" 슬라이스부터 하나씩 ReAct 루프로 바꿔나간다.
- 장점: 각 전환이 독립적이라 롤백이 쉽다(`agentic_realtime_info` 같은 플래그 하나로 전체를 되돌릴 수 있음). 계약을 건드리지 않아 프론트 변경이 필요 없다.
- 단점: 이동수단·RECOMMEND·SCHEDULE처럼 실패 조건이 애매하거나 상태가 복잡한 영역(예: `_score_recommendations()`가 리스트를 제자리에서 append하는 구조)은 같은 패턴을 그대로 옮기기 어렵다 — 슬라이스마다 "여기서 에이전트가 뭘 언제 멈춰야 하는가"를 새로 설계해야 한다. 전체가 다 넘어가기 전까지는 "일부는 LLM이 판단, 일부는 코드가 판단"하는 혼재 상태가 계속된다.

**방향 B — 인텐트 라우팅 자체를 범용 에이전트(`create_agent`형)로 한 번에 통합**
- 분류기·RAG·이동수단 판단·INFO 조회·추천 스코어링을 전부 도구로 등록하고, 인텐트 분기(`agent_runtime.py`의 if/elif)까지 LLM이 스스로 고르게 만든다. 90강이 말하는 "범용 에이전트"에 가장 가까운 형태.
- 장점: 새 기능을 추가할 때 라우팅 코드를 사람이 손대지 않아도 된다(도구 docstring만 추가). 인텐트 간 조합("반품 규정 찾아서 이 문의가 해당하는지 봐줘" 같은 복합 요청)도 자연스럽게 처리된다.
- 단점: `docs/design/langgraph-adoption.md` §9.9에 기록된 실측 문제가 이 방향의 구체적 리스크를 보여준다 — 멀티턴 상태를 LangGraph checkpointer로 프레임워크화했을 때 이전 턴 값이 유출되고, 세션당 체크포인트가 계속 쌓여 메모리가 늘었으며, `refill_execution` 같은 호출 기록이 상태 스냅샷 저장/복원 과정에서 조용히 사라지는 문제가 있었다. 즉 "한 번에 통합"은 계약 유지보다 **상태 관리 자체의 신뢰성**이 먼저 검증돼야 하는 방향이다.

### 정리 — 지금 어느 쪽으로 가고 있고, 무엇이 남았나

- 지금 코드는 방향 A(슬라이스별 확장)의 사례 하나(INFO)만 있고, 방향 B(전체 통합)는 시도된 적이 없다.
- 이동수단 판단은 두 방향 중 어느 쪽으로도 아직 옮겨지지 않은 상태 — 구조화 출력만으로 지금은 충분히 돌아가고 있어서 전환의 필요(=애매한 실패 조건, 반복 재시도 요구)가 아직 드러나지 않았다고 보는 게 정확하다.
- 방향 A를 계속 넓힌다면, 다음 후보는 "실패 조건이 INFO만큼 뚜렷한 곳"을 찾는 것이다. 이동수단은 "지원 안 되는 지역/구간" 같은 명확한 실패가 아니라 "여러 정답 후보 중 하나를 고르는" 문제라 INFO와 실패 구조가 다르다 — 그대로 옮기면 언제 재시도를 멈출지 기준이 없다는 문제에 부딪힐 가능성이 높다.
- 방향 B로 가려면 INFO 확장 여부와 무관하게, 상태 관리(checkpointer 유사 메커니즘)의 신뢰성 문제를 먼저 풀어야 한다. 이 문제를 풀지 않고 통합부터 하면 §9.9에서 실제로 발생했던 상태 유실이 다른 인텐트에서도 재현될 가능성이 있다.
