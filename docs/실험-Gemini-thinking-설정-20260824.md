## 1. 이 실험이 답하려는 질문

> **"모델이 새 버전으로 올라가면서, 설정을 요청하는 방식이 다 바뀐 건가?"**

결론부터 말하면 **"다 바뀐 것도, 그대로인 것도 아니다."** 두 방식이 한동안 **겹쳐서**
존재하고, 세대에 따라 되는 것과 안 되는 것이 갈린다. 그래서 "새 방식으로 갈아타면
끝"이 아니라, 어떤 모델을 쓰느냐에 따라 보내는 값을 골라야 한다.

---

## 2. 배경 — "생각"이 무엇이고 왜 끄려 했나

Gemini에는 답을 내기 전에 **스스로 한 번 더 따져보는 단계**가 있다. 이걸 "생각
(thinking)"이라고 부른다. 어려운 문제에는 도움이 되지만, 그만큼 **느려지고 비용도
더 든다.**

우리 서비스에서 이걸 끄고 싶었던 이유는 단순하다. "경복궁 근처 카페 추천해줘"가
추천 요청인지 아닌지 가려내는 것 같은 **단순한 판단**에는 깊이 생각할 필요가 없는데,
켜져 있으면 사용자가 그만큼 더 기다린다.

끄는 방법이 두 가지가 있고, **이 둘이 이번 이야기의 핵심**이다.

| 부르는 이름 | 어떻게 요청하나 | 언제 생긴 방식인가 |
|---|---|---|
| **예산 방식** | "생각에 쓸 분량을 0으로 줘" (숫자를 준다) | 옛 방식 |
| **레벨 방식** | "생각을 최소로 해줘" (단계 이름을 준다) | 새 방식 |

한 요청에 **둘 중 하나만** 넣을 수 있다. 같이 넣으면 오류가 난다.

---

## 3. 실험 1 — 어떤 모델이 어떤 방식을 받아주나 (전수)

같은 질문을 모델 5개에 4가지 설정으로 보내고, ① 요청을 받아주는지 ② 받아준다면
실제로 생각에 토큰을 몇 개 썼는지를 함께 기록했다. **②가 중요하다** — "최소로 해줘"가
이름만 최소인지 정말 생각을 끄는지는 이 숫자로만 확인된다.

생각 토큰 수는 3회 중앙값이다.

| 모델 | 예산=0 (옛 방식) | 예산=512 | 레벨=최소 (새 방식) | 설정 없음 |
|---|---|---|---|---|
| `gemini-2.5-flash` | ✅ 생각 0 | ✅ 생각 382 | ❌ **거부** | ✅ 생각 0~462 (들쭉날쭉) |
| `gemini-2.5-flash-lite` | ✅ 생각 0 | ✅ 생각 303 | ❌ **거부** | ✅ 생각 0 |
| `gemini-3.5-flash` | ✅ 생각 0 | ✅ 생각 221 | ✅ 생각 0 | ✅ 생각 377 |
| `gemini-3.5-flash-lite` | ❌ **거부** | ✅ 생각 0 | ✅ 생각 0 | ✅ 생각 0 |
| `gemini-3.6-flash` | ❌ **거부** | ✅ 생각 195 | ✅ 생각 0 | ✅ 생각 406 |

"거부"는 요청 자체가 잘못됐다는 오류(400)로 되돌아온 것이다. 답이 나쁘게 오는 게
아니라 **아예 실패한다.**

### 이 표에서 읽어야 할 것 네 가지

**① 새 방식은 옛 모델에서 아예 안 된다.** `gemini-2.5` 두 모델은 "레벨=최소"를
거부한다. 새 방식을 모르는 세대라고 보면 된다.

**② 옛 방식이 통째로 없어진 것은 아니다.** "예산=512"는 **모든 모델에서 성공**한다.
즉 숫자로 요청하는 방식 자체가 폐기된 게 아니다.

**③ 없어진 것은 "예산=0"이라는 특정 값 하나다.** 새 모델 중 둘(`3.5-flash-lite`,
`3.6-flash`)이 유일하게 이 값만 거부한다. 같은 방식의 다른 값(512)은 받는다.
**"방식이 바뀌었다"기보다 "한 값이 막혔다"가 정확한 서술이다.**

**④ 두 방식이 다 되는 구간이 있다.** `gemini-3.5-flash`는 옛 방식과 새 방식 모두
받는다. 세대가 딱 잘려서 넘어가는 게 아니라 **겹치는 구간을 두고 옮겨간다**는 뜻이다.

---

## 4. 실험 2 — "최소"는 정말 0인가

이름만 "최소"이고 실제로는 조금 생각하는 것일 수도 있다. 두 방식이 다 되는
`gemini-3.5-flash`에서 직접 비교했다.

| 보낸 설정 | 생각에 쓴 토큰 | 답변 |
|---|---|---|
| 예산=0 (옛 방식) | **0** | 같음 |
| 레벨=최소 (새 방식) | **0** | 같음 |
| 아무 설정 안 함 | **377** | 같음 |

**두 방식은 결과가 같다.** 둘 다 생각을 아예 하지 않았고, 설정을 안 하면 377토큰을
생각에 쓴다. 즉 새 방식으로 바꿔도 우리가 원했던 "생각 끄기"는 그대로 달성된다.

---

## 5. 실험 3 — 그래서 실제로 얼마나 빨라지나

여기서 예상과 다른 결과가 나왔다. **모델에 따라 효과가 극과 극이다.**

### 지금 우리가 쓰는 분류 모델(`gemini-3.5-flash-lite`) — 효과 없음

실제 인텐트 분류를 15회 번갈아 돌려 중앙값을 비교했다.

| | 응답 시간 |
|---|---|
| 생각 켜진 상태 | 958ms |
| 생각 끈 상태 | 949ms |
| 차이 | **-9ms (-0.9%)** |

이유는 표에 이미 나와 있다. 이 모델은 **설정을 안 해도 생각 토큰이 0**이다. 원래
생각을 안 하는 모델이라 끌 것이 없었다.

> **주의 — 표본이 적으면 여기서 잘못된 결론이 나온다.** 같은 측정을 6회로 돌렸을 때는
> -17%, -7%까지 나왔다. 15회로 늘리면 -0.9%로 수렴한다. 응답 시간은 호출마다 크게
> 흔들리므로 몇 회만 재고 결론을 내면 없는 효과를 있다고 착각한다.

### 생각을 많이 하는 모델(`gemini-3.6-flash`) — 효과 큼

| | 응답 시간 |
|---|---|
| 설정 안 함 (생각 406토큰) | 3,518ms |
| 레벨=최소 (생각 0토큰) | 1,416ms |

**2.5배 차이**다(각 1회 측정이라 참고값). 즉 이 설정의 값어치는 "어떤 모델을 쓰는지"에
전적으로 달려 있다.

## 6. 이번에 드러난 문제 두 가지

측정을 하다 실제 코드의 문제가 두 개 나왔다. 둘 다 **코드를 고친 적 없이 모델만
바꿨을 때** 생기는 종류다.

### 문제 1 — 생각 끄기가 조용히 무효화돼 있었다 (D-076에서 수정)

"예산=0을 거부하는 모델"에는 안전하게 **아무 설정도 보내지 않도록** 되어 있었다.
오류는 피하지만 **생각 끄기도 같이 사라진다.** 8월 18일에 분류용 모델을 그 목록에 있는
모델로 바꾸면서 실제로 그 일이 일어났고, 코드가 바뀐 게 아니라 모델만 바뀌었으니
**아무도 눈치채지 못했다.**

다행히 그 모델은 원래 생각을 안 해서 체감 피해는 없었다. 하지만 `3.6-flash`처럼 생각을
많이 하는 모델로 바꾸는 순간 2.5배 느려지는 것을 그대로 뒤집어쓴다.

### 문제 2 — 옛 모델로 되돌리면 전부 실패한다 (미해결)

지금 코드는 생각을 끌 때 **항상 새 방식(레벨)**을 보낸다. 그런데 실험 1에서 확인한
대로 `gemini-2.5` 모델은 새 방식을 거부한다. 실제로 지금 코드가 보낼 값을 그대로
보내봤다.

| 모델 | 호출 종류 | 결과 |
|---|---|---|
| `gemini-2.5-flash` | 분류·조건 추출·일정 편성 | ❌ 전부 거부(400) |
| `gemini-2.5-flash-lite` | 분류 | ✅ 성공(이 호출만 숫자 512를 보내므로) |
| `gemini-2.5-flash-lite` | 조건 추출·일정 편성 | ❌ 거부(400) |

즉 **옛 모델을 폴백으로 다시 올리면 그 순간 대부분의 호출이 죽는다.** 문제 1과 방향만
반대인 같은 종류의 함정이다.

### 해결 형태는 검증해 뒀다

목록을 "생각을 포기하는 조건"이 아니라 **"어느 방식을 보낼지 고르는 기준"**으로 쓰면
다섯 모델 모두 해결된다. 실제로 돌려 확인했다.

| 모델 | 보낸 방식 | 결과 |
|---|---|---|
| `gemini-2.5-flash` | 예산=0 | ✅ 생각 0 |
| `gemini-2.5-flash-lite` | 예산=0 | ✅ 생각 0 |
| `gemini-3.5-flash` | 예산=0 | ✅ 생각 0 |
| `gemini-3.5-flash-lite` | 레벨=최소 | ✅ 생각 0 |
| `gemini-3.6-flash` | 레벨=최소 | ✅ 생각 0 |

## 7. 발표에서 쓸 만한 이야기

- **"버전이 올라가면 옛 방식이 사라진다"는 단순한 그림이 아니다.** 옛 방식은 살아
  있고, 그중 특정 값 하나만 막혔다. 그래서 "새 방식으로 일괄 교체"가 오히려 옛 모델을
  못 쓰게 만들었다(문제 2).
- **코드를 안 고쳤는데 동작이 바뀌는 일이 실제로 있었다.** 설정 파일에서 모델 이름만
  바꿨는데 최적화가 사라졌고, 오류도 로그도 없어서 발견까지 6일이 걸렸다.
- **"안전하게 아무것도 안 보내기"가 안전하지 않을 수 있다.** 오류는 피했지만 원래
  목적을 조용히 포기하는 선택이었다.
- **몇 번만 재고 결론 내면 없는 효과가 보인다.** 6회에서 -17%, 15회에서 -0.9%.
  응답 시간 측정은 반복 횟수와 번갈아 재기가 결과를 좌우한다.
- **같은 이름의 모델도 세대에 따라 성격이 다르다.** `2.5-flash-lite`는 분량을 주면
  생각하지만(303토큰), `3.5-flash-lite`는 분량을 줘도 생각하지 않는다(0토큰).

## 8. 재현 방법

```bash
cd backend
python -m scripts.measure_fast_thinking_level --matrix --reps 3   # 실험 1·2 (전수 표)
python -m scripts.measure_fast_thinking_level --probe             # 어떤 설정이 거부되는지만
python -m scripts.measure_fast_thinking_level --reps 15           # 실험 3 (지연 비교)
```

실제 API를 호출하므로 `backend/.env`에 `LLM_API_KEY`가 있어야 하고, 외부 네트워크가
되는 환경에서 돌려야 한다. 자동 테스트(pytest)에는 넣지 않았다 — 호출 비용이 있고
결과가 모델 쪽 사정에 따라 달라지기 때문이다.
