## 1. 질문 둘

**Q1. FAST 쌍(인텐트 분류·조건 추출)의 주력이 `flash-lite`여도 되는가.**

2026-09-08 실측으로 **안 된다**는 쪽 증거가 나왔다. 조건 추출에서 흔들림 6/18 ·
기대 불일치 9/18이고, `flash`로 바꾸면 0/18 · 0/18이다. 그런데 단가가 입력 5배 ·
출력 3.6배라 그대로 올리기엔 비용이 걸린다.

**Q2. GENERATION 쌍(답변·일정 편성)은 반대로 `lite`로 내려도 되는가.**

팀에서 나온 의견이다. 지금 `flash`인데 문장 품질이 정말 필요한지 재본 적이 없다.
Q1의 비용 부담을 Q2로 상계할 수 있다면 전체 비용을 유지하면서 품질을 옮기는
선택이 된다.

**두 질문을 한 실험에서 함께 재는 이유가 그것이다.** 따로 재면 "추출을 올리면
비싸다"와 "답변을 내려도 된다"가 각각 결론만 남고, 합쳐서 얼마가 되는지 아무도
모른다.

## 2. 정확도를 어떻게 쓸 것인가 — 구간마다 다르다

선행 실험(`fallback_model_ab`)은 "정확도는 개선을 재는 눈금이 아니라 하락을 잡는
감지기"라고 못박았다. 이번엔 구간마다 정답의 존재 여부가 달라 판정 방법도 갈린다.

| 구간 | 정답셋 | 무엇으로 판정하나 |
|---|---|---|
| **1. 인텐트 분류** | **있다** — CSV의 `기대_intent` | 정확도(하락 감지) |
| **2. 조건 추출** | **없다** — 18필드 정답셋이 없고 그 정의는 프롬프트 소유다 | ① 페이로드 유실(이건 정답이 있다) ② 흔들림 ③ 모델 간 차이 |
| **3. 일정 편성** | **없다** — "좋은 일정"의 정답이 없다 | **계약 위반 횟수**(아래 §5) |
| **4. 답변 생성** | **없다** | 길이·지연만 기계로. 문장 품질은 사람 눈 |

### 2번이 왜 세 갈래인가

**조건 추출에는 부분적으로 정답이 있다.** 18필드의 값은 정답을 만들 수 없지만,
**"조건을 나르는 턴에 `recommend`가 통째로 없다"는 정답이 있는 실패다**(D-126).
그건 세면 된다.

나머지는 정답 없이 판정한다. `compare_extraction_models.py`가 세운 방식을 따른다 —
**`A ≠ B`는 기대값 없이 판정할 수 있다.** 여기에 같은 모델 반복(흔들림)을 더한다.
흔들림이 있으면 모델 간 차이가 모델 차이인지 분산인지 못 가른다.

### ⚠️ 흔들리는 모델에서는 대조군이 대조군 역할을 못 한다

0단계에서 실제로 당했다. `토요일 오후 2시부터 5시간 코스 짜줘`(본체)와
`5시간 코스 짜줘`(시간 조건만 남긴 대조군)를 짝지어 뒀는데, 1차에서 대조군이
통과하고 본체가 흔들려 "시작 시각 때문에 시간 값이 날아간다"로 읽혔다.
**3차에서는 대조군 쪽이 더 흔들렸다**(`300/null/null`).

**대조군도 같은 확률로 흔들리는 대상이면 짝 비교가 성립하지 않는다.** 대조군은
`flash`처럼 **고정이 확인된 조건에서만** 쓴다. lite 안에서의 짝 비교는 세 번 이상
반복하고 교집합으로 본다.

### ⚠️ 프롬프트를 고정한다는 것이 왜 이 실험의 전제인가

## 4. 무엇을 기록하는가 — 호출 하나마다

8월 실험 §6은 토큰을 "러너가 수집하지 않는다"는 이유로 제외했다. **지금은
`record_llm_call()`이 이미 토큰을 기록한다** — 그 공백을 이번에 닫는다.

| 기록 | 왜 |
|---|---|
| 요청 모델 / **실제 응답 모델**(`served_model`) | 폴백이 끼었는지. 끼면 그 회차는 비교에서 뺀다 |
| 재시도 횟수 | 지연·비용이 재시도로 늘어난 것인지 |
| 지연 ms | 체감 판단 |
| **입력 토큰 / 출력 토큰 / thinking 토큰 / 합계** | **비용 계산의 근거.** 단가와 곱한다 |
| **페이로드 전체 — null 포함** | 아래 |
| **null인 필드 이름 목록** | 아래 |
| 페이로드 자체가 `None`인가 | D-126의 실패 판정 |
| `status`(complete / needs_clarification) | 되묻기 턴과 유실 턴을 섞으면 평균이 무의미해진다(함정 30) |
| 오류 유형 | 429·타임아웃을 품질 문제로 오해하지 않기 위해 |

### null을 필드 이름으로 남기는 이유

기존 `compare_extraction_models.py`는 `model_dump(exclude_none=True)`로 덤프해
**null 필드를 아예 버린다.** 그러면 두 모델의 차이가 "값이 다르다"인지 "한쪽이
비웠다"인지 구분되지 않는다.

우리가 알고 싶은 것은 정확히 후자다. 그래서 이렇게 남긴다.

```
null_fields: ["current_location", "weather", "budget", "travel_origin", ...]
filled_fields: ["search_center", "time_available", "place_types"]
```

**필드별로 "이 모델이 이 필드를 얼마나 자주 비우나"를 셀 수 있어야** 문서에
"lite는 `time_available`을 3분의 1 확률로 비운다" 같은 문장을 쓸 수 있다.

## 5. 일정 편성은 계약 위반으로 판정한다

"좋은 일정"의 정답은 없다. 하지만 **`plan_schedule()`이 이미 하드 검증을 걸어
두었으므로 위반 횟수는 셀 수 있다.** 그게 곧 품질 지표다.

| 판정 | 무엇이 깨지나 |
|---|---|
| **항목 수 상한 초과** | `_cap_item_count()`가 잘라낸 건수. 지시가 아니라 계약이라 자르지만, 자주 잘리면 모델이 범위를 안 지키는 것이다 |
| **`must_include` 누락** | 담아둔 장소를 못 넣어 1회 재시도까지 갔는지, 그래도 빠졌는지(`omitted_saved_place_names`) |
| **체류시간 정책 범위 이탈** | `resolve_visit_duration()`이 클램프한 건수 |
| **예산 판정** | `within` / `over` / `under` 분포. `over`가 늘면 시간을 안 지키는 것이다 |
| **`warnings` 발생** | `planner`가 폐점 스탑을 감지한 건수 |
| 총 소요시간 · 항목 수 | 분포 비교 |

**이 값들은 이미 `schedule_quality` trace에 남는다**(TP-242). 러너가 같은 함수
(`schedule_quality_metrics()`)를 그대로 불러 쓰면 프로덕션과 같은 계산을 쓴다.

### 계산은 러너가 하지 않는다

토큰과 단가를 **따로 남기고 곱하는 것은 집계 쪽에 맡긴다**(`schedule/metrics.py`가
세운 "비율이 아니라 원자값" 원칙과 같다). 단가는 바뀌고, 실행 시점의 단가로 굳혀
두면 나중에 다시 계산할 수 없다.

### 문서에 반드시 넣을 표

**턴당 비용을 조합별로 낸다.** FAST와 GENERATION을 독립적으로 고를 수 있으므로
조합이 넷이다.

| FAST | GENERATION | 턴당 비용 | 품질 판정 |
|---|---|---|---|
| lite | flash | (지금) | (기준선) |
| flash | flash | | |
| **flash** | **lite** | | ← Q1·Q2를 함께 채택하는 안 |
| lite | lite | | |

**세 번째 행이 이 실험의 핵심 가설이다** — 품질이 필요한 곳으로 예산을 옮기는 것.

## 8. 판정 기준 (실행 전 확정)

**결과를 본 뒤에 기준을 정하면 실험이 아니라 사후 해석이 된다.**

### Q1 — FAST를 flash로 올릴 것인가

| 결과 | 판정 |
|---|---|
| 추출 페이로드 유실이 flash에서 0이고 lite에서 1건 이상 | **flash 채택 근거로 충분** |
| 분류 정확도 하락 4건 이상 (모수 64) | lite 기각 |
| MODIFY·RECOMMEND·SCHEDULE에서 5/5 재현 오답 | **건수 무관 lite 기각** (8월 기준 그대로) |
| 위 어느 것도 아니고 흔들림도 없음 | lite 유지 — 9/8 관측이 재현되지 않았다는 뜻이므로 원인을 다시 찾는다 |

### Q2 — GENERATION을 lite로 내릴 것인가

| 결과 | 판정 |
|---|---|
| 일정 편성에서 계약 위반이 lite에서 1건이라도 늘면 | **기각.** 상한·필수 포함은 사용자에게 직접 보이는 결함이다 |
| 계약 위반 동일 + 답변 눈가림 채점에서 유의한 하락 없음 | **조건부 채택** — 한계를 문서화하고 되돌리기 쉬운 상태로 둔다 |
| 계약 위반 동일 + 채점도 동일 | **채택** |

### Q2-b — 구간 이동수단 판정 (`judge_travel_modes`) **[2026-09-09 추가]**

GENERATION 스위치에 묶인 호출부 중 **기계로 판정할 수 있는 마지막 것**이다
(`호출부_지도.md` §3). 4단계와 달리 **거리 규칙이라는 고정 기준선**이 있어서
정답 없이도 채점된다.

**flash 기준선은 이미 있다** — `mode_judge_2026-09-03/`, repeat 3, 14조건 42호출,
**세 회차가 전부 동일**했다(흔들림 0). 그래서 **lite만 잰다**(14호출).

| 조건 묶음 | flash 기준선 | lite 판정 기준 |
|---|---|---|
| **무반응** (없음·맑음) | 규칙일치 6/6, 전환 3 | **6/6이 아니면 실패.** 조건이 없는데 규칙과 갈리면 근거 없이 바뀐 것이다 |
| **반응** (비·비+유모차) | 규칙일치 4, 전환 5 | **전환이 3에서 늘지 않으면 실패.** 비를 얹었는데 안 바뀌면 조건을 안 읽는 것이다 |
| **접근성** (유모차·휠체어·노인동행) | 전환 4~5 | 전환이 3보다 커야 한다. 방향만 본다 |
| **일관** | 모든 조건에서 첫 줄이 walking, 일정/추천 동일 | 같은 조건의 일정/추천 **첫 줄**이 갈리면 실패(D-118 환산 관계) |
| 지연 | p50 1,123ms · p95 1,328ms | 참고값. 판정에 쓰지 않는다 |

**하나라도 실패하면 GENERATION은 flash로 확정되고 5단계는 돌지 않는다.**
전부 통과하면 5단계(답변·요약 6종)로 넘어간다 — 그쪽은 사람 눈 검사가 필요하다.

**반복 1회로 시작한다.** flash가 3회 동일했으므로 흔들림은 lite에서 갈릴 때만
재면 된다. 갈린 조건이 나오면 그 조건만 `--only`로 좁혀 `--repeat 5`를 올린다.

### 비용 판정

**절대 금액으로 정하지 않는다.** 팀의 실제 턴 수를 모르면 "감당 가능"을 정할 수
없다. 대신 **조합별 배수**로 적고, 판단은 턴 수를 아는 사람이 한다.

## 9. 측정하지 않는 것과, 이미 알고 있는 것

### 이미 기각된 것 — 다시 재지 말 것

| 안 | 근거 |
|---|---|
| **lite + thinking** | `../intent_experiments_2026-08.md` §4. flash보다 **느리고**(2,118ms 대 1,588ms) **덜 정확**했다(59/64 대 63/64). thinking 토큰도 과금된다 |
| **재랭킹을 lite로** | D-117. flash-lite로 내리면 +6.8%p가 +0.9%p로 사라진다 |

### 측정하지 않는 것

| 제외 | 이유 |
|---|---|
| 프롬프트 축소 | 비용의 대부분이 입력이라 효과가 크지만 **규칙을 빼면 품질이 바뀐다.** 모델 변수와 섞으면 둘 다 못 가른다. 별건 |
| 실제 폴백 전환 빈도 | 이 실험은 "그 모델이 답했을 때의 품질"만 본다. 9/8 실측에서 폴백은 0/18이었다 |
| 빈손일 때 flash 재시도(D-126 후보 d) | 구현이 없다. 이 실험 결과로 필요성이 정해진다 |
| 토큰 단가의 원화 환산 | 환율이 변수다. USD로 남기고 환산은 집계에서 |

### 이번에 함께 확인할 발견 둘

**발견 1 — `verify_schedule_condition_extraction.py` 머리말이 낡았다.**
".env는 주 모델 gemini-3.5-flash에 폴백 gemini-2.5-flash-lite"라고 적혀 있는데
실제 기본값은 `gemini-3.5-flash-lite`다(`config.py:323`, 2026-08-18 `89b5bdf`부터).
**스크립트가 첫 줄에 실제 묶음을 출력하니 그것을 근거로 쓴다.**

**발견 2 — `compare_extraction_models.py`가 SCHEDULE을 건너뛴다.**
주석이 "SCHEDULE은 별도 편성 프롬프트를 쓰고"라고 적었는데 **틀렸다.**
`orchestrator.py:369`가 SCHEDULE에도 `extract_recommend_conditions()`를 그대로 쓰고
intent만 바꿔치기한다. **그래서 우리 문제의 핵심 케이스 7건(51~56·59)이 통째로
빠져 있었다.** 2단계 실행 전에 고쳐야 한다.
