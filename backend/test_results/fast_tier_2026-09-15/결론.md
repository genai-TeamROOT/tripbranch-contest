# FAST 티어 모델 결정 — `gemini-3.5-flash-lite`를 유지한다

| 항목 | 값 |
|---|---|
| 측정일 | 2026-09-15 |
| 정하는 것 | `LLM_FAST_MODEL_NAME` 한 줄. FAST는 9개 호출부를 묶는다 |
| 실 사용량 | 골드셋 **396턴**(3모델 x 131턴 + 스모크 3) · 추적 측정 **92호출** |
| 원자료 | `../agent_quality/runs/2026-09-15_*_103cases_c210d85f009e` · `../classify_gap_2026-09-15/` · `../extract_homonym_2026-09-15/` |
| 코드 변경 | 없음. 측정 스크립트 `CASES`에 대조군 넷을 더한 것이 전부다 |

> **결론: FAST는 `gemini-3.5-flash-lite`로 둔다.**
>
> `gemini-3.6-flash`가 품질에서 위이지만 **지연 p50 +2.2초 · p95 +5.3초와 호출당 2.18배**를
> 치른다. 그 값을 치를 만큼의 차이인지가 쟁점이었는데, **갈린 자리를 하나씩 뜯어보니
> 3.5-lite에 남은 결정적 실패가 둘뿐이고 둘 다 모델이 아니라 프롬프트·라벨 자리였다.**

---

## 1. 왜 다시 쟀나

2026-09-08 실험(`../model_tier_2026-09-08/`)이 프롬프트 `recommend.extract@2.8.0`에서
lite 계열을 기각했다 — 조건 추출 기대 불일치 9/18, 흔들림 4~6/18.

2026-09-14에 `extract.md`의 출력 계약을 고쳐(2.9.0) **그 실패를 12건에서 0으로 닫았다**
(`../prompt_extract_fix_2026-09-14/`). 그 문서가 남긴 숙제가 이것이다.

> 남은 일은 전체 재측정이다. 골드셋을 2.9.0에서 다시 돌려야 한다.

**즉 기각 근거가 낡았는지를 확인하는 실험이다.**

## 2. 1차 — 골드셋 전체 (3모델 x 103건 / 131턴)

골드셋 dev · `digest=c210d85f009e` · `recommend.extract@2.9.0` · `router.classify@2.7.0`.
GENERATION은 세 arm 전부 `gemini-3.5-flash`로 **고정**했다(변수를 하나로 둔다).

**DEV-097은 arm1에서 HTTP 502(`state_store_error`, Supabase 타임아웃)로 죽어
세 arm 전부에서 뺐다.** 아래는 102건 / 128턴 기준이다.

| 축 | 3.5-lite | 3.1-lite | 3.6-flash |
|---|---|---|---|
| Intent Accuracy | 97.66% | 96.88% | **99.22%** |
| Macro F1 | 0.9782 | 0.9723 | **0.9938** |
| 조건 필드 정확도 | 98.82% | 98.24% | **99.41%** |
| 케이스 통과 | 97/102 | 96/102 | **100/102** |
| 지연 p50 / p95 | 9,499 / 23,941ms | 10,035 / 25,444ms | **11,703 / 29,286ms** |
| 캐시 적중 | 0 | 10.6% | 9.6% |
| 호출당 단가 배수 | 1.00배 | 0.76배 | **2.18배** (2027-01-01부터 4.36배) |

세 실행 모두 `fast_models_served`가 단일 모델이고 digest가 같다 — **유효하다.**

### 두 가지를 그대로 읽으면 안 된다

**① 스크립트가 찍는 "직전 실행 대비" 델타.** arm2에 `조건 필드 +0.0229`가 찍혔는데
**개선이 아니다** — arm1 기준선에 502가 섞여 있었다. 같은 조건으로 다시 재면 **-0.59%p로
뒤집힌다.** (RULES 함정 75)

**② 조건 필드 정확도의 분해능.** 채점은 케이스가 `expected_final_conditions`에 적은
필드만 센다 — dev 103건에서 **총 175건**이다. **1건이 0.57%p**라, 세 arm의 차이는
전부 +-1건이었다. 숫자가 아니라 어느 필드가 틀렸는지를 본다.

## 3. 2차 — 갈린 자리만 반복 측정

골드셋은 반복 1회다. "때때로 맞는다"와 "맞는다"를 못 가른다. 그래서 **갈린 케이스만**
떼어 5회씩 다시 쟀다(`agent_quality/README.md`의 "전수 1회 -> 갈린 케이스만 5회" 설계).

### 3-1. 분류 — 51호출 (`../classify_gap_2026-09-15/`)

| 번호 | 발화 | 기대 | 3.5-lite | 3.1-lite |
|---|---|---|---|---|
| 1 | `경복궁 근처 카페 추천해줘` (대조군) | RECOMMEND | 5/5 | 5/5 |
| 21 | `다른 곳 보여줘` | MODIFY | **5/5** | **5/5** |
| 41 | `벚꽃 언제 피어?` | GENERAL | 3/5 | 0/5 |
| 101 | `연희동은 어떤 동네야?` | GENERAL | **0/5** | 5/5 |
| 102 | `비 와서 실내로 바꿔줘` (문맥 없는 첫 턴) | RECOMMEND | 4/5 | **0/5** |

**21번이 5/5로 통과했다.** 골드셋 DEV-027에서 3.5-lite가 틀린 것이 모델 단독으로는
재현되지 않는다. 이 러너는 `classify_intent()`에 문맥 인자를 넷만 넘기고 프로덕션은
셋을 더 넘긴다(`orchestrator.py:528-536`) — **더 실린 문맥이 흔든 것일 수 있다.**
어느 쪽이든 모델을 바꿔 고칠 문제가 아니다.

**41번은 판정에서 뺐다.** `gemini-3.5-flash`도 0/3으로 틀리고 3.6-flash만 맞혔다.
`../model_tier_2026-09-08/3.6-flash_결과.md`가 19·41·47을 "기대값 논쟁적 · 라벨 확정 보류"로
지목해 뒀다.

## 5. 3.1-lite를 고르지 않는 이유

두 lite 모두 결정적 실패가 하나씩인데 **성질이 다르다.**

| | 결정적 실패 | 범위 |
|---|---|---|
| 3.5-lite | 추출 — `수유`+`유모차` 조합 | **좁다.** 규칙 한 줄이 닫고 회귀도 그 조합에 한정 |
| 3.1-lite | 분류 — 문맥 없는 첫 턴을 MODIFY로 | **넓다.** 문맥 유무를 안 읽는다. MODIFY 축 전체가 회귀 범위 |

3.1-lite는 단가 0.76배에 캐시 41%까지 걸려 비용 우위가 실측으로 확인됐다. 그러나
MODIFY와 RECOMMEND를 문맥으로 가르는 것은 이 제품의 기본 동작이다.
**그 분류 건이 닫히면 다시 볼 값이 있다.**

## 7. 곁들여 나온 것 셋

**① 자동 캐싱은 모델이 가른다.** 같은 프롬프트 · 같은 발화 · 호출당 입력 4,199토큰으로
똑같은데 3.1-lite는 41%가 캐시에서 읽히고 3.5-lite는 0이다. 4,199는 문턱(4,096)을 넘으므로
"크기 미달"도 "접두가 매 턴 달라짐"도 원인이 아니다. 2026-09-08의 "103토큰 모자라 도달
불가"는 그때 프롬프트 기준이고 2.9.0에서는 크기 문제가 아니다.

**② 분류 프롬프트는 캐싱을 못 받고 있다.** 입력 4,469토큰으로 문턱을 넘는데 적중 0이다.
2026-09-08이 "분류 프롬프트의 실측 토큰은 아직 모른다"로 남겨둔 항목의 답이다.
닫으면 이 호출의 입력 비용이 열 배 내려간다.

**③ 재랭킹에 지뢰가 있다.** `place_mood_rerank_model_name`이 미설정이라 FAST를 따르는데,
`config.py:212` 주석이 "flash급이어야 한다 — 3.5-flash-lite로 내리면 개선이 +6.8%p에서
+0.9%p로 사라진다(TP-213)"고 적어놨다. **FAST가 lite인 지금 켜면 기각된 모델로 돈다.**
`place_mood_rerank_enabled`가 기본 False라 지금은 안 돈다. **FAST를 lite로 확정하면
`PLACE_MOOD_RERANK_MODEL_NAME`을 flash급으로 명시해 둔다.**
