# 서울시 실시간 도시데이터 대상 지역

서울시 실시간 도시데이터 API(`citydata`/`citydata_ppltn`/`citydata_cmrcl`)는 좌표가 아니라
`AREA_NM`(지역 이름)으로 조회한다. 우리는 사용자 좌표를 가장 가까운 지역 이름으로 바꿔서
조회하므로, "그 서비스가 아는 지역 이름 전체 목록 + 대표 좌표"가 있어야 한다. 이 폴더가
그 목록이다.

| 파일 | 내용 | 조회 대상 API |
| --- | --- | --- |
| `population_areas_121.json` | 121개 지역 (POI 코드·이름·영문명·카테고리·대표 좌표) | `citydata`(통합), `citydata_ppltn`(인구 전용) |
| `commercial_areas_82.json` | 82개 지역 (121개의 부분집합, 같은 필드) | `citydata_cmrcl`(상권 전용) |

## 왜 파일이 두 개인가 — 서비스마다 대상 지역 수가 다르다(2026-08-26 확인)

서울시가 공개한 두 공식 목록을 직접 받아 대조했다.

- 인구 혼잡도: [서울시 실시간 인구데이터](https://data.seoul.go.kr/dataList/OA-21778/A/1/datasetView.do) →
  `서울시 주요 121장소 목록(코드포함).xlsx`, `서울시 주요 121장소 영역.zip`(경계 SHP)
- 상권 활동: [서울시 실시간 상권현황](https://data.seoul.go.kr/dataList/OA-22385/F/1/datasetView.do) →
  `서울시 주요 82장소 목록.xlsx`

두 목록을 코드 기준으로 비교하면 **82개 전부가 121개의 부분집합**이고(82에만 있고 121에
없는 코드 0개), 121에만 있는 39곳은 대부분(33곳) **공원**이고 나머지는 고궁·문화유산 3곳
(경복궁·창덕궁·종묘·서울 암사동 유적)과 인구밀집지역 6곳(삼각지역·숭례문 등)이다.

그런데 기존 코드(`app/agent_context/seoul_realtime_areas.py`의 전신, 옛 이름
`seoul_commercial_areas.py`)는 상권용 82개 목록 하나로 좌표→지역 변환을 다 처리하고
있었다. 그 결과 인구 혼잡도를 물어도 "경복궁"으로는 못 찾고 더 먼 "광화문·덕수궁"으로
대체되는 식의 불필요한 정확도 손실이 있었다(TP-141이 신고한 증상) — `citydata`/
`citydata_ppltn` 둘 다 "경복궁"을 직접 지원하는데도 우리 목록에 없어서 놓친 것이다(실제
호출로 확인: 두 API 모두 `AREA_NM=경복궁`에 동일한 값을 정상 반환한다).

**82곳은 121곳을 "아직 못 따라간" 목록이 아니라, 서울시가 처음부터 정한 영구적인
부분집합이다.** 서울시가 배포하는 공식 매뉴얼(`실시간 도시데이터 매뉴얼 V8.5`, 2026-04,
36p)에 이렇게 적혀 있다: "정확한 정보 전달을 위해 서울시 주요 장소 121장소 중 가맹점
수가 적거나, 소비가 적은 장소를 제외한 82장소에 대해 서비스 제공." 카드소비 데이터가
통계적으로 의미 있으려면 가맹점이 일정 수 이상 있어야 하는데, 공원 33곳 등은 애초에 그
조건을 못 채운다 — 시간이 지나 82가 121로 갱신될 문제가 아니다. 그래서 상권 조회 경로는
앞으로도 계속 `commercial_areas_82.json`만 쓴다.

`app/agent_context/service.py`의 세 조회 경로가 각각 어느 목록을 보는지(TP-141/D-084):

| 조회 경로 | API | 목록 |
| --- | --- | --- |
| `_fetch_realtime_population_or_concentration_info` | `citydata`/`citydata_ppltn` | 121개 |
| `_fetch_realtime_commercial_info` | `citydata_cmrcl` | 82개 |
| `_fetch_realtime_city_info`(주차·지하철·버스·행사) | `citydata`(통합) | 121개 |

## 좌표는 어떻게 만들었나

두 파일 모두 `population_areas_121.json`과 같은 SHP(`서울시 주요 121장소 영역.zip`)의
폴리곤에서 **면적가중 중심(centroid)**을 계산했다(shoelace 공식). 82개 목록도 이전에는
별도로 받은 좌표를 썼는데, 지금은 121개와 같은 SHP·같은 계산식으로 다시 뽑아 82/121이
서로 다른 기준으로 어긋나지 않게 했다 — 기존 값과 비교했을 때 평균 오차는 위도·경도 각각
0.001도 미만(대략 수십~수백 미터)이었다.

## 지역이 늘어나면

서울시 매뉴얼 48p에 "시민 의견을 수렴하여 지속적으로 확대, 현행화 예정"이라고 명시돼
있다 — 인구 목록(121개)은 시간이 지나면 늘어날 수 있다(상권 82개는 위에서 설명한
이유로 앞으로도 구조적으로 갱신되지 않을 가능성이 높다). 목록이 늘면 위 두 링크에서
새 xlsx/SHP를 받아 같은 방식으로 다시 뽑아 이 폴더의 파일만 교체하면 된다.
코드(`seoul_realtime_areas.py`)는 파일을 그대로 읽으므로 손댈 곳이 없다 — 다만 로더가
카테고리별 개수를 매뉴얼 표와 대조해 검증하므로, 매뉴얼도 같이 갱신된 버전을 참고해
`_EXPECTED_CATEGORY_COUNTS`를 맞춰야 한다.

`app/agent_context/service.py`의 낡음 감지 probe(TP-141/D-084)가 121개 목록이 서울시
라이브 API보다 뒤처지기 시작하면 개발자 화면 배너로 알려준다 — 목록을 언제 갱신해야
할지 신경 써서 추적하지 않아도 되는 이유다.
